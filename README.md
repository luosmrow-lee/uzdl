# uZDL

A launcher for ZDoom based Doom source ports: pick a port and an IWAD, add PWADs, keep the combinations you play as presets, and browse the idgames archive without leaving the launcher. A fork of [Lcferrum's ZDL](https://github.com/lcferrum/qzdl) - which targets Qt 4.8 and no longer builds on current toolchains - ported to Qt 6 and extended.

## Features

- **Presets** - named sets of PWADs, patches and configs, each optionally with its own source port and IWAD, and its own save folder and settings file so a mod's saves never mix with the vanilla game's. Those two show on the tab the preset was loaded on while they apply, and stop applying once another port or game is picked there by hand, so they never carry over unseen to the next game. The Doom Engine and Build Engine tabs each list their own presets: a preset belongs to the tab its source port is for, or its game when it names no port. Load, append or launch one in a click; pin the ones you play most to the top and sort the rest by name; edit it beside the PWAD library; import and export as `.zdl`; make a desktop shortcut that starts straight into it, which also serves as a Steam entry.
- **A tab for the Build engine** - the Build engine's games have a tab of their own, *Build Engine*, beside *Doom Engine*: presets, the mods loaded over the game (GRPs, zips, scripts, definitions, maps, and whole folders for mods that come as a folder of files, such as Zombie Nukem), and the source port and game with map, skill and respawning monsters, in a launch configuration of its own, so starting Duke Nukem 3D never disturbs the Doom setup or the other way round. Each tab lists only its own engine's ports and games: EDuke32, Rednukem, NBlood, PCExhumed, VoidSW, BuildGDX and Raze go to the Build Engine tab. A Build game set up on the single launch tab of earlier versions moves over by itself, and a `.zdl` file or a shortcut's preset opens on the tab it was made for.
- **PWAD library** - a folder of your choosing, scanned recursively and watched for changes, with a filter and Folders / Newest / Name views. Select files or a whole folder and add them to the launch; the right-click menu also moves or deletes them and opens their folder.
- **idgames browser** - the whole /idgames archive, searchable offline from a mirror's own listing, with each entry's description. Installs straight into the PWAD folder, marks what is already installed, and opens the entry's Doomworld page for reviews and screenshots.
- **Finds your games** - *Find installed* on the General settings tab looks where Steam, GOG, the Bethesda launcher and the ports themselves keep IWADs and source ports, identifies every IWAD by its contents the way GZDoom does, and adds what you tick. A first start with nothing set up offers the same search. On Windows a port's name and version come from its executable, so three GZDoom installs show up as three versions.
- **Knows the Build games** - Duke Nukem 3D and its add-ons, Blood, Shadow Warrior, Redneck Rampage, NAM, WWII GI and PowerSlave are told apart the way Raze and EDuke32 tell them, by a file's exact size and CRC32, from those ports' own tables; a `.grpinfo` file beside a game is read as they read it, Route 66 and Cryptic Passage are recognised inside a zip by the files they hold, and a few total conversions no port's table has, such as Quest for Hussein and Liquidator 3D, by their file names. Witchaven, Witchaven II, TekWar and Legend of the Seven Paladins, which come as folders of loose files, are told by the files their folder holds, the way BuildGDX tells them, and so is Liquidator unpacked from its zip; any of their own files in the IWAD list, `TILES000.ART`, `TABLES.DAT` or a script, stands for the game. Route 66 and Cryptic Passage, which the GOG and Steam releases ship as loose files in Redneck Rampage's and Blood's folders, are told by their script, `GAME66.CON` or `CRYPTIC.INI`, with their two art files beside it; Cryptic Passage also in Fresh Supply's `addons\Cryptic Passage` folder. An add-on no port's table knows, such as a repacked Penthouse Paradise, is told by the files it holds, and any other GRP of a Duke add-on is named after the episodes its own scripts define, "Duke Nukem 3D add-on: Plug and Pray", or by its file when it keeps Duke's episodes first. A mod that comes as a folder of loose files over Duke Nukem 3D is told by its main script, `EDUKE.CON` or else `GAME.CON`, in a folder with maps and episodes of its own, "Duke Nukem 3D mod: Horror Castle"; the folder itself goes in the Build Engine tab's mods, and *File information* on it says so. An add-on of Blood's is told by the INI that defines its episodes, "Blood add-on: Death Wish", after its folder, for the INI and for its folder alike. *Find installed* offers all of these, a folder game once and add-on zips by what they hold. A GRP added to the IWAD list gets its real name, *Find installed* looks in the Steam, GOG and ZOOM folders of these games and never copies one away from the files it needs, and *File information* shows the game, its CRC32, the base game an add-on needs, the maps and scripts in a GRP and the ports that run it.
- **Game patches** - fixes for known faults in games' own files, the kind today's source ports stop on where the original game carried on, on the uZDL settings tab. A fix is tied by MD5 to the exact file it was written for and changes only the lines it names, so any other version is left alone; the original is kept beside the fixed file as `.uzdl-original`, and *Undo* puts it back. Where the ports read the file out of the game's GRP, a fixed copy is written beside the GRP instead, which they read first, and *Undo* removes it. A fix is offered for a game's folder only when the game's own GRP is in it, since games can share a script. The fixes so far are for Plunder & Pillage and the two Quest games built on its scripts, Quest for Al-Qa'eda and Quest for Hussein, which make EDuke32 abort: an `else` with no `if` in `GAME.CON`, which the DOS games passed over, and a misspelt action that kept the blimp from respawning. *File information* mentions a fix on any file or GRP it applies to.
- **File information** - from the *uZDL* menu, or a right click on any file in the lists and the library: what a file is and holds. An IWAD and which release; a PWAD with its maps and their formats, the sprites, sounds and definition lumps in it, its DeHackEd patch, and which ports it needs; an archive; a demo and the game it was recorded on; a source port and its version. Any file can be dropped on the window.
- **Raze set up for you** - Raze, the Build engine port of the ZDoom family, plays Duke Nukem 3D, Blood, Shadow Warrior and their add-ons, and takes a game file through `-iwad` like the Doom ports. It only plays an add-on when it also finds the base game in a folder it searches, and on Windows keeps its settings and saves per user unless told otherwise. When Raze is added as a source port, uZDL offers to set it up: a `raze_portable.ini` beside `raze.exe`, with the settings Raze used until then, so that it keeps its settings and saves with it; and the folders of the Build games in the IWAD list added to the folders Raze searches, which uZDL keeps up to date at every launch. A `grps` folder in the uZDL folder Raze lives in is taken as the place for Build games and goes in twice: as `$UZDL_DIR/grps/*`, which Raze expands from a variable uZDL sets for every port it starts, so it holds at any depth and after any move; and as `../../grps/*`, relative to Raze's own folder, for the times Raze is started by hand. Both are found from Raze's own location, so it does not matter which configuration uZDL runs with or whether any of the games is listed yet. Games elsewhere are added from the IWAD list: folders that share a parent go in as that parent with `/*`, relative to Raze's own folder when the two live in the same uZDL folder, as they are otherwise. The rest of Raze's ini is left as it is, a no is remembered, and *Set up Raze for uZDL* on the port's right-click menu runs the setup again at any time. A game Raze does not know by its checksum, a total conversion such as Quest for Hussein, Liquidator's folder, a mod's folder or an add-on in a form no table has, is loaded with `-file` over a Duke game named with `-iwad`, Atomic first, beside it or from the IWAD list, with its own main script given with `-con` where that is not `GAME.CON`. Route 66's and Cryptic Passage's loose files get Raze's own `-route66` and `-cryptic` switches over their base game, which also load the add-ons' extra art; an add-on kept in a folder of its own, as Fresh Supply keeps Cryptic Passage, has that folder added with `-file`.
- **The EDuke32 family** - EDuke32, Rednukem, NBlood, PCExhumed and VoidSW get a command line of their own. Pick the game file on the Build Engine tab, a GRP, Blood's INI, Exhumed's STUFF.DAT or Shadow Warrior's GRP, and Launch starts it straight away: the game's folder goes to the port with `-j`, the file with `-gamegrp` or `-ini`, Shadow Warrior's add-ons by their number, and `-nosetup` keeps the port's own window out of the way. EDuke32 and Rednukem only take a file named with `-gamegrp` when they know it by its checksum and find the base game it needs; otherwise they quietly start a game they do know. So a file they know is named with `-gamegrp`, with the folder of its base game added from the IWAD list when that is kept elsewhere; any other, a repacked Penthouse Paradise, Duke!ZONE, a mod's zip, is loaded with `-g` over the base game, Atomic first, named with `-gamegrp`, with the add-on's own main script, `PPAKGAME.CON` or the one its `.grpinfo` names, given with `-x`. A total conversion, which needs no base game, is named with `-gamegrp` and loaded with `-g` as well, so that it wins whether or not the port finds a game of its own. NBlood plays Cryptic Passage from its `CRYPTIC.INI`, with Blood's folder searched too when the add-on is kept in a folder of its own. Any other add-on of Blood's whose episodes are in an INI of its own, Death Wish among them, plays the same way: the INI picked as the game, or the INI or its folder in the mods, goes to NBlood with `-ini`, by name, with its folder searched and Blood's found for it, since NBlood takes the INI only from a folder it searches, and its startup window, where such an INI is otherwise picked, stays closed. A script picked as the game, a mod's main script above all, has the base game named with `-gamegrp` and its folder searched, Atomic first, beside it or from the IWAD list, so a mod unpacked anywhere starts over Duke Nukem 3D. The mods list goes by type, `-g` for archives, `-x` for the first CON script and `-mx` for the ones after it, `-mh` for a DEF, `-map` for a map, and `-j` for a folder, a mod that comes as a folder of loose files: named after the game, since the ports search the folder named last first, so that the mod's files win over the game's, with the GRPs and zips in it loaded with `-g`; with no game picked, the first mod that needs a base game, a Duke mod's folder or an add-on GRP or zip the port does not know, on its own or in a folder, gets Duke Nukem 3D named under it, Atomic first, as it would picked as the game; skill, no monsters, respawning, the map field, a preset's save folder and config file are translated to each port's own words, and what a port has no word for is left out. A big game or mod gets a bigger cache by itself: these ports keep tile art and sounds in a cache of 96 MB unless told otherwise, and quit with "CACHE SPACE ALL LOCKED UP!" when a level needs more, as Savior of Babes does, so a launch handing the port more than 256 MB of game data gets `-cachesize` with half that, rounded up to 64 MB, from 256 to 512 MB. A cache size in the port's own parameters or the extra ones is left to stand, and the ports remember the size in their own config file, so one set larger there is never lowered. The port's own parameters and the extra ones follow as always.
- **BuildGDX** - the Java port that plays Duke Nukem 3D, Blood, Shadow Warrior, Redneck Rampage, PowerSlave and NAM, and also Witchaven, Witchaven II, TekWar and Legend of the Seven Paladins, is started straight into the game: the game's folder goes to it with `-path` and the game by BuildGDX's own name for it with `-game`, so its launcher window stays closed. Add-ons and user maps are picked in its menus.
- **Per-port parameters** - arguments a source port always gets, plus a *Run* button that starts a port on its own, which is how ports with a built-in updater get to update.
- **Portable** - opt in with an empty `uzdl_portable.ini`; anything kept inside the uZDL folder is stored relative to it, so the folder moves or copies as one.
- **Updates itself** - checks the GitHub releases on demand or once a day, shows the release notes, and on Windows, and on Linux when run as the AppImage, downloads the new version, verifies it against the checksum GitHub publishes, installs it over the old one and restarts. Your configuration and files are never touched; *Skip this version* silences a release you do not want.
- Themes (System, Light, Dark), multiplayer setup, demo playback and file associations, as in ZDL; on Linux the `.zdl` type is registered with the desktop.

## Download and install

- Releases: https://github.com/luosmrow-lee/uzdl/releases - a zip for Windows and an AppImage for Linux, each with everything needed; there is nothing to install.
- Windows: unpack the zip anywhere and run `uzdl.exe`.
- Linux: make the AppImage executable (`chmod +x uZDL-*.AppImage`) and run it. It carries its own Qt and needs a distribution with glibc 2.39 or newer, which means Ubuntu 24.04, Debian 13, Fedora 40 or anything more recent.
- Building from source: see [COMPILE](COMPILE).
- uZDL is only a launcher: you need a source port and the game's IWAD separately.

## Portable mode

- Create an empty file named `uzdl_portable.ini` beside `uzdl.exe`, or beside the AppImage on Linux, and it becomes the only configuration uZDL reads or writes. Without it the configuration is per-user, as in ZDL. *Portable mode* in the uZDL menu does the same without leaving uZDL: ticking it writes the current configuration into that file and keeps it there from then on; unticking it writes the configuration back to the per-user file and sends `uzdl_portable.ini` to the recycle bin.
- Neither release package contains the file, so unpacking a newer version over an old folder, or swapping in a newer AppImage, never touches your configuration.
- A port, an IWAD, the PWAD folder, and the files in the launch list and in presets are stored relative to the uZDL folder whenever they sit inside it. For ports and IWADs the add and edit dialogs tick *Relative to the uZDL folder* by default and can keep the absolute path instead; `sourceports` and `iwads` folders are created for the purpose.
- The folder has to be somewhere writable, since the configuration lives beside the executable. A folder under Program Files will not work without elevation.
- File associations are the one feature that reaches outside the folder, into the Windows registry, and only when you press the button.
- To carry a per-user configuration into a portable one, copy it over `uzdl_portable.ini`: `%APPDATA%\Vectec Software\qZDL.ini` on Windows, `~/.config/Vectec Software/qZDL.ini` on Linux.

## Using it

Five tabs:

- **General settings** - the source ports you have and the IWADs and Build games you own, added by drag and drop or the buttons, each port with its own parameters, and the parameters always added to every launch.
- **uZDL settings** - everything about uZDL itself in one place: closing on launch, remembering the file lists, starting .zdl files without the window, the theme, file paths in the lists, how presets sort, where the configuration lives and portable mode, the PWAD library folder, the idgames mirror, file associations, updates and a skipped release, the Raze ports and whether each is set up, game patches to apply or undo, and buttons for Find installed, File information, the command line, loading and saving .zdl and .ini files, importing an old ZDL configuration and About.
- **Doom Engine** - from left to right the PWAD library, the presets, the external files for this launch (in load order; an entry can be disabled to keep it in the list but off the command line), and the source port and IWAD with map, skill, compatibility mode, fast and respawning monsters, and multiplayer options. *Launch* starts the game; the *uZDL* menu shows the command line about to run.
- **Build Engine** - the same for the Build engine's games: the presets, the mods for this launch, and the source port and game with map, skill and respawning monsters, each with its own extra command line arguments. *Launch* starts the game, *Launch preset* loads the selected preset and starts it, and the *uZDL* menu shows the command line about to run.
- **idgames** - *Update index* once to fetch the listing, then narrow it by type, age and name. *Download and install* unpacks the selection into the PWAD folder, where the library picks it up.

Quickstart:

1. On General settings, add your source ports and IWADs.
2. On Doom Engine, choose a port and an IWAD and add files from the PWAD library; for a Build game, choose a port and the game on Build Engine and add any mods.
3. Press *Launch*.
4. When a combination is worth keeping, press *Save as preset*. Next time, select the preset and press its *Launch*.

The port and IWAD lists, both tabs' launch configurations, pane widths and window size are all remembered between sessions.

A preset can be started from outside uZDL too: `uzdl --preset "Name"` loads it and launches the game, which is what the *Shortcut* button on the presets pane writes into a desktop shortcut. Presets are written to the configuration file the moment they are saved, edited or deleted, rather than when uZDL closes, so a shortcut works with uZDL still open; a shortcut finds its preset by name, and one whose preset was renamed or deleted says so and closes without touching the configuration. Add that shortcut to Steam as a non-Steam game and the preset appears there like any other title.
